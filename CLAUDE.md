# Shipbytes Design System

A portable design system for new projects. Ships as two packages from one repo:

| Package | Registry | Who needs it |
|---|---|---|
| `shipbytes/blade-ui` | Composer | Laravel + Blade. Ships the compiled CSS, so no npm step. |
| `@shipbytes/design-tokens` | npm | Anything else — plain HTML, Svelte, a chart palette. |
| `@shipbytes/react` | npm | **No longer maintained.** |
| `@shipbytes/vue` | npm | **Will not be built.** |

**Target release: 2.0.0**, built on the `next-2.0` integration branch: Blade only,
plus the package's first script of its own (see The shared script).
`@shipbytes/react` was started under `packages/` on the `react` branch; it is
not maintained, master has none of it, and nothing here builds, tests or
documents it. Leave `packages/` and that branch alone. There will be no
`@shipbytes/vue`. Anyone not on Blade takes `@shipbytes/design-tokens`.

**The registries are separate front doors and each renders its own metadata.**
Packagist shows only the `description` field — no README — so that sentence is
the whole signpost there. npm renders README.md **from the package's own
directory**, and includes it automatically even when `files` does not list it:
the root README is what `@shipbytes/design-tokens` shows, which is why it opens
with a "which package do I need?" table rather than with Blade install steps.

Published at `github.com/shipbytes/design-system` and on Packagist as
`shipbytes/blade-ui`, so a consumer needs one `composer require` and no
repository block.

It was extracted from a production dashboard rather than designed in the
abstract. That is why the specs argue from measured usage ("zinc-500 was the
most-used class, 850 times") instead of taste. Those numbers are the evidence
for the rules and are worth preserving when editing.

## Layout

```
composer.json     shipbytes/blade-ui       ← both manifests live at the ROOT.
package.json      @shipbytes/design-tokens   Composer reads composer.json from
                                             the repo root and nowhere else.

src/              the service provider
  View/Components/Scripts.php   ds::scripts, the include (a class, not a view)
  Http/ScriptController.php     serves the script at the route the include links
  Support/Behaviour.php         the x-data expression for a shared behaviour
  Support/Field.php             reads the field recipe (partials/field.php)
config/           blade-ui.php — icon aliases, default icon size
resources/views/  the Blade components + the two pagination views and
                  their two Livewire variants
                  (everything here SHIPS to consumers — keep it lean)
  partials/bar.blade.php        the track and fill progress and usage-meter
                                share; a partial, not a component, because it
                                carries no role or value of its own
  partials/field.php            the field recipe: ds::input's class strings
                                (shell, control, label, help, error), which
                                otp-input, tag-input and number-field draw
                                with too. Plain PHP under resources/views so a
                                consumer's Tailwind scans it; ds::input's 1.x
                                output is held byte for byte by
                                InputUnchangedTest
resources/js/     the shared script's source: plain ES modules, hand-edited
  blade-ui.js       the Alpine plugin; lists every behaviour
  global.js         the classic-script entry ds::scripts serves
  behaviours/       one file per behaviour
                  (export-ignored: consumers get dist/, not the modules)

tokens/           DTCG source. Edited by hand, like resources/js/.
dist/             generated by `npm run build`. Never edit.
  blade-ui.js         the plugin as an ES module (Vite: Alpine.plugin)
  blade-ui.global.js  the classic script, comments stripped (ds::scripts)
specs/            one markdown per component: anatomy, variants, states, a11y
docs/             CONSUMER docs: how to use each component, with screenshots
                  images/ is generated by `npm run build:docs` and committed
icons/            which Heroicons the system uses, and their v2 names
scripts/          build + test, and gallery.blade.php (dev-only, not shipped)
tests/            testbench render tests. Specimens.php IS the coverage.
phpunit.xml       dev-only; neither file ships to consumers
```

## Commands

```bash
npm run build        # tokens/ + resources/js/ -> dist/   (after ANY change to either)
npm run build:tokens     # just the tokens
npm run build:js         # just the script
npm run build:icons -- <path-to-app>   # manual: re-derive icons/icons.json from an app
npm test             # tokens, script, render, then behaviour
npm run test:tokens      # structure, WCAG contrast, theme collisions, motion utilities
npm run test:js          # dist/ current, registrations, components <-> script
npm run test:render      # renders every component through testbench
npm run test:behaviour   # drives every interactive one in a real browser
npm run build:gallery    # dist/gallery.html
npm run build:docs       # docs/images/ — re-run whenever a component's look changes
```

`build` is tokens and the script, nothing that needs anything outside the repo.
Until v1.3.0 it chained `build-icons.mjs`, which needs the path of an app to
read and exits 1 without one, so `npm run build` failed on every clean clone
after writing `dist/` correctly. `icons/icons.json` is checked in; `build:icons`
is the deliberate, rare step of re-deriving it.

**None of these need a host application.** `scripts/render.php` boots Laravel
through testbench, so the gallery, the screenshots and the behaviour tests all
render through the same three lines and a clean clone needs nothing but
`composer install` and `npm install`.

`npm test` must pass before any commit. Four suites:

**Tokens** (`test-tokens.mjs`) — structure, WCAG contrast in both themes, theme
collisions, and that the motion tokens compile to working `duration-*` /
`ease-*` utilities, under `motion-safe:` too. No Blade involved.

**Script** (`test-js.mjs`) — `dist/blade-ui*.js` match what `resources/js/`
builds to (ds::scripts serves the COMMITTED file, so stale means stale in
production); the script registers only `ds`-prefixed names, only through
`Alpine.data` / `Alpine.directive`, once however often it loads; and the
components and the script agree — every name a view asks for is registered,
every name registered is used by a view or documented in getting-started.

**Render** (`test-render.mjs`) — boots Laravel, renders every component in
`tests/Specimens.php`, and asserts every class it emits has a rule in CSS
compiled the way a *consumer* compiles it. Also enforces that every component
appears in the gallery, in the docs specimens, and has a documentation page,
and renders every specimen a second time inside a Livewire component to catch a
morph marker landing inside a tag (see Traps).

**Behaviour** (`test-behaviour.mjs`) — drives every interactive component in a
real browser with real Alpine: focus traps, arrow keys, what the form actually
posts. The main page is host setup (a), ds::scripts in the head above a
deferred Alpine file; pages of their own cover (b) `Alpine.plugin()` on the ES
module, (c) Livewire's bundled Alpine with the include loaded twice, a
Content Security Policy with and without the nonce, and a page with no include
that must say what is missing. Every request for `http://localhost/…` is
answered by Laravel itself through `scripts/request.php`, so the include's src
is fetched from the package's real route, headers and all. **Skips with a warning when there
is no Chromium** (`npx playwright install chromium`), so a clean clone still goes
green — read the warning.

## How to actually verify a change

```bash
npm run build:docs      # regenerates docs/images/ — light and dark, side by side
npm run build:gallery   # dist/gallery.html — every component on one page
```

The screenshots are drawn in Inter, embedded into the page from the
`@fontsource-variable/inter` dev dependency, never from the host's fonts or a
CDN. Before 2.0 they used whatever sans the machine had, so a rebuild on
another machine rewrote every image. Each shot is also photographed alone at
the top of the page, because text rasterises slightly differently by position
and a new specimen used to shift and rewrite every image below it. An image now
changes only when its component does, and the build refuses to shoot if Inter
did not load.

**Look at the rendered output, in a browser, in both themes.** Every serious bug
in this repo's history was invisible in the source and obvious in a picture: the
panel inheriting the browser's default black at 1.4:1, the modal overflowing its
container, the dropdown detaching from its trigger in a flex row, the icon
rendering at the height of its panel.

`npm test` now covers a great deal of this — rendered classes, behaviour in a
real browser, and a contrast audit inside `build:docs` that fails the build on
anything under 3:1. What none of it can see is **a class that exists and is
wrong**. Both of these were green under `npm test` and obvious on screen:

- the modal's `max-h-[calc(100dvh-2rem)]` measured the viewport rather than the
  box it was centred in, so a long modal overflowed its container;
- the dropdown's root was `inline-block`, so in a flex toolbar it stretched to
  the row height and the menu opened from the floor of it.

So: still look at it.

## The consumer contract

```bash
composer require shipbytes/blade-ui
```

```css
@import 'tailwindcss';
@import '../../vendor/shipbytes/blade-ui/dist/tokens.css';
@import '../../vendor/shipbytes/blade-ui/dist/theme.css';
@source '../../vendor/shipbytes/blade-ui/resources/views';
```

```blade
{{-- in the layout's head, above Alpine's script tag (or Livewire's) --}}
<x-ds::scripts />
```

Three lines, not four — `theme.css` brings its own `@custom-variant dark`. It
also carries `[x-cloak] { display: none !important }`, which Alpine expects every
project to write by hand: nine components mark their overlay root `x-cloak`, so
without it every dialog on the page renders open, backdrop and all, until Alpine
boots. That is our failure to ship, not the consumer's to remember.
No npm step: the composer package ships `dist/`.

Requires Tailwind v4. Dark mode is a `dark` class on `<html>`.

## Traps that have already bitten, in this repo

Each of these failed **silently**. None threw an error.

**Tailwind does not scan `vendor/`.** Without the consumer's `@source` line
every class the components emit is discarded as unused and everything renders
unstyled. "Unused" is not a failure, so nothing reports it. This is the single
most likely thing to go wrong in a new project.

**A class built at runtime is invisible to the scanner.** The icon component
composes `size-{$size}`; Tailwind reads source *text*, and `size="4.5"` is not
the string `size-4.5`. `theme.css` therefore carries an `@source inline(...)`
list, generated by `build-tokens.mjs` from the components plus a base range —
the base range exists so a *consumer* passing `size="7"` in their own view also
works. `npm test` fails if a component asks for a size the list misses. **Any
new component that builds a class from a prop needs the same treatment.**

**An `@theme` key overwrites Tailwind's, it does not add to it.** This is why
radius and shadow are named for the job (`control`/`panel`/`chip`,
`raised`/`float`/`overlay`) and not `sm`/`md`/`lg`. Reusing those keys would
resize every existing `rounded-lg` in the host app. `npm test` guards this with
a collision check whose only allowed entry is `--font-sans`.

**A `var()` inside a custom-property declaration resolves at the declaring
element.** `--color-x: var(--ds-x)` on `:root` bakes in the light value, and a
`.dark` ancestor cannot retroactively change it. `build-tokens.mjs` therefore
re-declares every themed mapping inside `.dark`. Remove that and dark mode dies
quietly for every semantic utility.

**Blade emits an uncompiled component tag as literal text** when the tag
contains a multi-line attribute-bag expression. Build the bag in `@php` and pass
it as `:attributes`. `build-gallery.mjs` fails the build if it sees `<x-ds::` in
rendered output, because that is the signature.

**Foreground tokens are `fg`/`fg-muted`, not `text-*`.** Tailwind's `text-*`
namespace serves both colour and font size, so `semantic.text-muted` would
generate the utility `text-text-muted`.

**`php artisan tinker --execute` rewrites the markup it prints.** PsySH's output
pipeline turns `...` into `..`, so every spread operator in a component lost a
dot on the way out. `build-gallery.mjs` rendered through tinker, so the modal's
focus trap and the dropdown's arrow-key handler both reached the gallery as
`[..$el.querySelectorAll(` — a syntax error, thrown at runtime, in a page that
looked perfect. Worse than a broken component: the gallery inventing a break
that does not exist in the shipped code. It now boots the framework directly and
carries a canary string through the render to prove nothing rewrote it.

**Blade's component-tag compiler is text-level, and does not know what a
comment is.** `<x-ds::tab-panel>` written inside a PHP doc comment in `@props`
was compiled into a real component invocation, in the middle of the props array,
and the file stopped making sense — the error was "Undefined variable $component"
pointing at a compiled file in storage, naming nothing. **Never write a component
tag in a comment.** Write `ds::tab-panel` without the angle brackets.

**Livewire reads comments too, and a plain HTML tag in one is enough.** Livewire
4 wraps every `@if` and `@foreach` in `<!--[if BLOCK]>` markers and skips one
that sits inside an opening tag, deciding that by looking back through the RAW
template for the nearest `<` that starts a tag. The button's attribute bag
carried the comment "A bare `<button>` defaults to type=submit"; that literal
became the nearest `<` before `@if ($disabled || $loading)`, so Livewire judged
the `@if` to be outside the tag and put a marker INSIDE the real button. Every
`ds::button` in every consumer running Livewire rendered as "> Save", with the
`>` in its accessible name, and clicks still worked. A plain-Blade render shows
nothing, because the markers only exist while Livewire is rendering a component.
**Never write any tag with angle brackets in a component's comments**, HTML or
Blade: write "a bare button element", the `nav` landmark. `LivewireMarkersTest`
renders every specimen inside a Livewire component and fails on a marker inside
a tag; it is the one test that boots Livewire, which stays a dev dependency.

**A Blade DIRECTIVE inside a component tag's attribute is not compiled at the
call site.** `<x-ds::icon x-show="v === @js($option['value'])">` inside a
`@foreach` hands the directive to the CHILD as a literal string, where it is
evaluated in the child's scope and `$option` does not exist; `@unless` on a
component tag instead makes the tag parser give up and print the tag. `{{ }}`
echoes are fine there. Build the value in `@php` and echo it.

**An anonymous component turns only DECLARED props into variables.** Everything
else lands in `$attributes`. So `<x-ds::nav-item icon="home">` — where `icon` is a
SLOT — leaves `$icon` undefined, the `@isset` around it false, and the row renders
with no icon at all. The mirror case is just as quiet: a `<x-slot:head>` that no
component renders is simply dropped, which is how the table specimen, the docs
and the documentation screenshot were all wrong together. `npm test` now checks
both directions.

**A random id is a new element to Livewire.** Every form control generated its
default id from `uniqid()`. Livewire's morph keys elements by id, so each
response REPLACED every bound field instead of patching it, and a replaced field
loses focus and caret: in a live search the first burst of typing landed and
everything after the first response went to the page body. Validation looked
fine, tests were green, and the kit's admin search only showed it when a person
paused mid-word. `Support\ControlId` now hashes the binding, name, value and
label for a control with `wire:model`, and keeps the random id for one without,
so two look-alike plain-Blade fields still get two ids. `ControlIdTest` holds
both halves.

**`ds::icon`'s `fallback` is opt-in, and must stay so.** An unknown name throws
`Unable to locate a class or view for component [heroicon-o-…]`, because in a
template a wrong name is a developer error. A consumer fed names from config into
the icon, one entry was a v1 name with no alias, and every page showing that nav
was a 500, including the one where it could be fixed. `fallback="…"` renders a
stand-in and logs one warning per request per name; pass it only where the name
is data. The existence check and the render both resolve through
`Support\Icons::component()`: give them separate copies of the alias or variant
logic and the check passes names the page then throws on. `IconFallbackTest`
holds both halves and the alias case.

**A prop that resolves to classes in PHP cannot be driven from Alpine.** Every
`tone`, `variant`, `size` and `active` is a lookup of literal class strings, done
once at render time — which is the only reason Tailwind's scanner can see them.
So `::tone="item.tone"` binds an attribute nothing reads, and an `x-for` over a
toast list renders every toast neutral. Nothing errors. The repair has a second
trap inside it: Alpine's STRING form of `:class` only *adds* classes, so the
server-rendered `border-transparent` survives and the element carries both. Only
the OBJECT form removes a class the server put there. `specs/tabs.md` documented
the broken form for two releases; the working one is now a driven specimen in
`scripts/behaviour-specimens.blade.php` so it cannot drift back.

**`open` on modal, drawer and sheet is an lvalue, not an expression.** They
assign to it — `@click="{{ $open }} = false"` — so `open="mode === 'x'"` compiles
to `mode === 'x' = false`. The dialog OPENS, because reading is fine, and then
the ✕, the backdrop and Escape all do nothing, with a clean server log and one
console `SyntaxError`. `Support\OpenState` now refuses it at render time. The
check is deliberately shallow — comparison and logical operators only. It must
not grow into a JavaScript parser: a false positive here is worse than the bug,
because the bug at least renders.

**An anonymous component silently drops a slot it never renders.** `empty-state`
has no default slot — its body is `title`/`description` and the button goes in
`action` — so passing buttons the way every other component takes them rendered
nothing at all. It throws now. Same shape as the `<x-slot:head>` the table
ignored, and as `<x-ds::nav-item icon="home">` leaving `$icon` undefined.

**A missing ds behaviour names itself, and a missing ds DIRECTIVE says nothing.**
In a host without ds::scripts, `x-data="dsClipboard"` reached Alpine as
`Alpine Expression Error: dsClipboard is not defined` — verified, and accurate,
but it names the behaviour rather than the include, so it reads like a bug in
the package. `Support\Behaviour::data()` writes the x-data instead: it tests
`typeof` first and throws "dsClipboard is not registered: add the ds::scripts
tag above the Alpine script…", which Alpine prints and the browser reports as
uncaught. A DIRECTIVE has no such hook: Alpine skips an `x-ds-*` it has no
handler for, in silence, the same way it skips `x-trap` without the focus
plugin. So a component never relies on a directive alone; `test-js.mjs` fails a
view that uses `x-ds-*` without a `Behaviour::data()` scope, and one that writes
a bare `x-data="ds…"`.

**`defer` on an INLINE script does nothing.** The behaviour harness wrote Alpine
into the head as an inline script marked `defer`, which runs on the spot and
starts Alpine before the body is parsed. Harmless for eight releases, because
nothing had to happen before Alpine started; the shared script does, and an
include placed after that inline Alpine would have listened for an
`alpine:init` that had already fired. The harness now loads Alpine as a FILE
with `defer`, the way the CDN snippet does. `build-docs.mjs` still inlines
Alpine, but at the END of the page, after the include.

**Tailwind v4 auto-detects sources on top of `@source`.** Compiling anywhere
inside the repo silently pulls in `scripts/gallery.blade.php`, `dist/gallery.html`
and the specs — all of which *mention* the classes the components emit. The
render test compiled against that passed while deliberately broken, because
something else in the repo happened to name the class. `@import "tailwindcss"
source(none)` plus one explicit `@source` is what makes the check mean anything.
A consumer's own import should auto-detect; ours must not.

## Conventions

- **Presentation only.** No Livewire, no application state, no framework
  assumptions beyond Blade and, where behaviour needs it, core Alpine (no
  plugins, no other library; native browser APIs with a fallback where support
  is partial). Anything reactive is passed in by the host through attributes. This is what keeps the same markup usable from plain Blade, a
  Livewire component, or a Volt page. The ONE deliberate exception is the
  pagination views' opt-in Livewire mode (`ds::pagination-livewire`,
  `ds::simple-pagination-livewire`), which emits `wire:click`, because
  Livewire's `WithPagination` replaces the default view and a link would reload
  the page. Livewire stays a dev dependency, used only by the tests.
- **A component is not done until SEVEN things exist.** In the same commit
  series, not as follow-up work:
  1. the component in `resources/views/components/`
  2. its **spec** in `specs/` — anatomy, variants, states, the a11y contract, and
     a "Do not" section. Sub-components (`table-cell`, `panel-row`) are covered
     by the parent's spec.
  3. a **specimen** in `tests/Specimens.php` — that list *is* the test coverage,
     so a variant missing from it is a variant nothing renders
  4. a **docs page** in `docs/components/` — usage, full prop table, examples
     against real Laravel, accessibility, and a "Don't" list
  5. a **specimen** in `scripts/docs-specimens.blade.php`, then
     `npm run build:docs` to generate its light/dark screenshot
  6. a **section in `scripts/gallery.blade.php`**, then `npm run build:gallery`.
     The gallery claims to render every component in both themes; six shipped
     without one and quietly made that false.
  7. for anything interactive, a **specimen and assertions** in
     `scripts/behaviour-specimens.blade.php` and `scripts/test-behaviour.mjs`

  **And if it uses a behaviour from the shared script:** the behaviour in
  `resources/js/behaviours/` and in `BEHAVIOURS`, `npm run build`, the x-data
  written through `Support\Behaviour::data()`, the behaviour's row in
  getting-started's "What it registers", its own assertions in
  `test-behaviour.mjs`, and the docs callout
  `> **Needs Alpine** and the package's script. See [getting started](../getting-started.md#3-add-the-script).`
  in place of the plain Alpine one.

  `npm test` enforces 3, 4, 5 and 6, and the registration half of the paragraph
  above. Nothing enforces 1, 2, 7 and the docs callout but you.
  A component reported as done without its documentation page is unfinished.
- **Semantic props, not free-form styling.** `tone="danger"`, not
  `tile="bg-red-50"`. A prop that takes a class string is an escape hatch that
  becomes the norm — the sheet shipped with ten decorative hues that way.
- **Every animation is `motion-safe:`, or has an explicit reduced-motion
  branch.** A transition is `motion-safe:transition`, so with reduced motion
  the change still happens, at once. Durations and curves come from
  `tokens/motion.json` through their utilities — `duration-popover-enter`,
  `ease-enter` — never a bare `duration-150`: pick the pair for the kind of
  surface (`hint`, `popover`, `dialog`, `slide`) and use `-leave` on the way
  out. A JavaScript animation (the stat tile's count-up) checks
  `matchMedia('(prefers-reduced-motion: reduce)')` and skips. The components
  built before 2.0 predate this rule; see Known gaps.
- **Comments explain why, not what.** The reason a value is what it is, or the
  bug that made it necessary.
- **Never name the app this came from.** It is deliberately anonymous.

## The shared script

From 2.0 the package ships one small script of its own, which registers
reusable behaviours with Alpine. Before that every component wrote its Alpine
inline and the package shipped no JavaScript.

**Where code goes.**

- `resources/js/behaviours/<name>.js` — one behaviour per file, exporting one
  `function <name>(Alpine)` that makes the registration(s). Module-level helpers
  are private to the file (the build wraps each module in its own function).
- `resources/js/blade-ui.js` — the plugin. A new behaviour is one import and
  one entry in `BEHAVIOURS`. Nothing else in here.
- `resources/js/global.js` — the classic entry. Do not add behaviour to it.
- `scripts/build-js.mjs` turns those into `dist/blade-ui.js` (ESM, readable)
  and `dist/blade-ui.global.js` (classic, whole-line comments and leading
  indentation stripped, safe because no string spans lines). It
  accepts a deliberately small set of module shapes — `import { a } from
  './x.js'`, `import x from './x.js'`, `export function`, `export default
  function`, `export const` — and refuses anything else by name. Relative
  imports only: **zero dependencies**, and no bundler.
- No template literal may span lines (the comment stripper is line-based, and
  the build refuses one), and nothing may contain the sequences that end an
  inline script element (the build refuses those too).

**Naming.** Data: `Alpine.data('dsPascalCase', …)`, used as
`x-data="dsOtp(…)"`. Directives: `Alpine.directive('ds-kebab', …)`, used as
`x-ds-glide`. Nothing else is registered — no magics, stores or global `bind`s
— until a batch needs one and adds it here first; `test-js.mjs` fails any other
`Alpine.*` call at registration. A behaviour names the job (`dsClipboard`), not
the component that first used it.

**What a behaviour's scope exposes is API.** Everything an `Alpine.data` object
returns is visible to the markup inside it and shadows the host's variables of
the same name. Return the state and methods the markup needs and keep options,
timers and helpers in the closure. `dsClipboard` exposes `copied` and `copy`
and nothing else.

**How a component asks for one.** Always through the helper, echoed:

```blade
@php $state = \Shipbytes\BladeUi\Support\Behaviour::data('dsClipboard', ['text' => $value]); @endphp
<div x-data="{{ $state }}">…</div>
```

An array becomes a JSON object; a string is a JavaScript expression, inserted
as written. The helper is what turns a missing include into an error naming it
(see Traps).

**When inline Alpine is still right.** State that is one or two keys and a
toggle, read by that one component and no other: the tooltip's `tipOpen`, the
dropdown's scoped flag. The line is roughly ten lines of Alpine, or a second
component wanting the same thing; past either, it is a behaviour. Behaviour
that has to be right before Alpine boots is PHP, not either of these.

**Delivery.** `<x-ds::scripts />` writes a classic script element whose src is
a route the package registers, `/{prefix}/blade-ui.{hash}.js` (prefix
`blade-ui`, from `config('blade-ui.script.prefix')`), where the hash is the
first 16 hex characters of the built file's xxh128. `Http\ScriptController`
serves it as `text/javascript` with `Cache-Control: public, max-age=31536000,
immutable` and an ETag (a matching `If-None-Match` gets a 304); a request for a
hash that is not the current one, from a page rendered before a deploy, gets
today's file marked `no-cache`, so it works and the new file is never pinned to
the old URL. The route is registered straight on the router in no group, so no
session, cookie, CSRF or auth middleware runs; it is a controller, not a
closure, and is skipped under `routesAreCached()`, so `route:cache` keeps it;
and its URL comes from `route()`, absolute, so an app in a subdirectory gets
its base path. `ScriptsTest` holds all of that, cached routes and a
subdirectory request included.

The element has **neither `defer` nor `async`**, on purpose: a parser-blocking
external script in the head has run before a deferred Alpine and before
Livewire's script at the end of the body, which is what lets it register on
`alpine:init`. The behaviour suite checks that, in setups (a) and (c), by
asking at `alpine:init` whether the plugin has already registered, and the
check fails if the include is moved behind Alpine with `defer`.

`inline` (`<x-ds::scripts inline />`) writes the file into the page instead:
the escape hatch for a page that cannot reach the route, such as the gallery
and the documentation screenshots, which are files opened from disk. The
`nonce` prop sets a CSP nonce in both forms, defaulting to the one given to
`Vite::useCspNonce()`. The output renders through an `HtmlString`, never
through Blade, so a `{{` or an `@` in the JavaScript cannot be compiled. It is
a class component so that the seven-artifact tests, which glob
`resources/views/components`, do not have to learn an exemption. Hosts that
bundle Alpine import `dist/blade-ui.js` and call `Alpine.plugin(bladeUi)`
instead.

Until batch 03 the include inlined the file. Inline had been chosen over a
route because a route has to survive route caching, subdirectory installs and
the host's middleware; at ~19 kB after five behaviours, uncacheable on every
page, the route was worth that work, and the tests above are the work. A copy
published to `public/` is still not an option: it goes stale on
`composer update`, silently, and the old behaviour keeps running.

**Two outputs because one file cannot be both.** A classic script cannot
contain `export`, and a module script is always deferred, so it runs after a
non-deferred Alpine or Livewire script above it and registers too late.

**Loading twice is harmless**, by design and by test: the plugin marks the Alpine
it registered on with `Symbol.for('shipbytes.blade-ui')`, which two separate
copies of the script (the include's and a Vite import) both see.

**Testing a behaviour.** Drive it in `test-behaviour.mjs` on the main page (host
setup a); the setup (b) and (c) pages and the no-include page reuse the
`#clip` specimen, and a new behaviour only needs adding there if it registers
differently. `test-js.mjs` needs nothing per behaviour. The two outputs are
generated, so after editing `resources/js/` run `npm run build` before
`npm test`, or the staleness check fails first.

table-row, tabs, tag-input, toast, toast-region, tooltip, usage-meter.

**Every built component has a spec.**

Verified end to end: `composer require` from GitHub into a fresh Laravel app,
three lines of CSS, every component rendering styled in light and dark.

**Needs Alpine:** modal, drawer, sheet, dropdown, select, combobox, date-picker,
accordion (with accordion-item), file-upload, tooltip, otp-input, tag-input,
number-field, password-strength — always. Plus ONE optional prop each on
checkbox (`indeterminate`), nav-item (`collapsedWhen`), toast (`dismiss`) and
input (`reveal`), and the pagination views' Livewire variants, whose scroll to
the top is an `x-on:click` that Livewire's bundled Alpine runs. Everything else
is plain Blade and CSS (stat-tile's count-up is a plain script it pushes to a
`scripts` stack), and nothing anywhere needs Livewire; the pagination views'
Livewire variants are opt-in. Counted from the directives in the views on
`next-2.0`, not from the docs.

**Needs the shared script:** otp-input (`dsOtp`), tag-input (`dsTagInput`),
number-field (`dsNumberField`), password-strength (`dsPasswordStrength`), and
input's `reveal` (`dsPassword`). It also registers `dsClipboard`, which the
copy button will build on.

**How those behaviours are written** (batch 02 set the pattern): the Blade view
renders the whole correct state, value and disabled flags included, and marks
the parts with `data-ds-*` hooks; the behaviour finds them in `init()`, wires
its listeners on `this.$el` and removes them in `destroy()`, and exposes
nothing else. The script never adds a class: a consumer's Tailwind only sees
classes in resources/views, so visual state travels as an attribute
(`hidden`, `aria-pressed`, `data-level`) that a variant in the view reads, and
a cloned `template` carries any markup the script has to create. The strings a
behaviour speaks are passed in from the view, in English.

The alert's dismiss used to be Alpine's `@click` and is now a plain `onclick`:
nothing else in that component needs JavaScript, and with `@click` the ✕
rendered, looked pressable, and did nothing at all in a host without Alpine.

`modal`, `drawer` and `sheet` emit Alpine directives and own no state — the host
declares `open`, the component reads and writes it. `dropdown` and `tooltip`
scope their own, because their state is local to one trigger and a kebab menu per
table row would otherwise need a wrapper `x-data` each. `accordion` scopes which
section is open, because exclusivity is a relationship between the items.
`select`, `combobox`, `date-picker` and `file-upload` scope their UI state — the
open flag, a mirror of the chosen label, the file list — while the FORM value
posts through a real input exactly as a native control would.

Modal's and drawer's focus traps are written out longhand rather than using
`@alpinejs/focus`: **Alpine skips a directive it has no handler for**, so in a
host without the plugin `x-trap` is not an error, it is nothing at all — and
`aria-modal="true"` becomes a claim the DOM does not honour.

**Components render their state correctly before Alpine boots.** `select`
renders the selected option's tick and the trigger's colour from PHP, so there
is no flash of wrong state on first paint and the markup is right in anything
that never runs the JS. Bind for what moves; render what does not.

## Known gaps

Kept here so nobody has to rediscover them. Roughly in the order worth closing.

**1. No overlay knows where the viewport edge is.** `dropdown`, `select`,
`combobox`, `date-picker` and `tooltip` each take a placement and trust it.
`npm run test:behaviour` now MEASURES the cost at the bottom of its run rather
than describing it. **Read the number as a floor, not the overflow.** It scrolls
each trigger to the bottom of the window only as far as the specimen page can
scroll, so it grows with the page: the date picker read 32px until v1.2.1 added a
specimen above it, and 106px after, with nothing about the picker changed. A
calendar is ~340px tall, so the real figure is larger, and the dropdown and the
select "fitting" may say as much about the page as about them. Pad the page
before trading on it.

Fixing it properly means floating-ui, which would be this package's first real JS
dependency. The number is there so that trade can be made on evidence.

**2. The npm package is unpublished.** `@shipbytes/design-tokens` does not exist
on the registry, so the `import { tokens } from '@shipbytes/design-tokens'` path
in the README does not work yet. Irrelevant to Blade consumers — the composer
package ships `dist/` — and only blocks a JS project.

**3. `fg-muted` and `danger` are under AA on the app's own ground.** 4.39:1 and
4.33:1 on `surface-sunken`, against the 4.5 they need; both are comfortable in
dark (7.56, 6.93). It matters for help text, a breadcrumb, or a form that sits on
the page rather than inside a panel.

Recorded as ADVISORY in `test-tokens.mjs` rather than fixed, because closing it
means moving `fg-muted` off zinc-500 — the most-used colour in the system. A
deliberate decision with a wide blast radius, not a quiet fix.

**4. The components built before 2.0 ignore reduced motion.** Their
`x-transition` classes are plain `transition ease-out duration-150` and the like,
not `motion-safe:`, and the numbers are literals rather than the motion
utilities (the tokens were derived FROM those numbers, so the values agree).
Moving them over is a restyle of existing components, which batch 00 was told
not to do. The skeleton's pulse and the stat tile's count-up already honour it.

**5. The gallery cannot show `sheet` or `bottom-nav`.** Both are `lg:hidden`, and
the gallery is a page a person opens on a desktop, so at that viewport they
render nothing. The gallery's sheet section is hand-drawn markup for this reason
and is the one place in it that is not the real component. `bottom-nav-item` is
not affected: the media query is on the bar, so the gallery shows real items in a
bar drawn to match, and `RendersComponentsTest` requires it there. The documentation
screenshots DO show them, because that script drives a 1000px viewport on
purpose. An `<iframe>` at phone width would fix it.

**6. The accordion cannot be found by find-in-page.** It is the ARIA disclosure
pattern, so a collapsed section is `visibility: hidden` and the browser's own
find will not reveal it. `<details>` would give that for free, and was the other
candidate — see specs/accordion.md.

**7. A table row cannot be a link.** `table-row` never had the `href` its docs
described until v1.2.1; it rendered `<tr href>`, which nothing reads. The docs now
say to link a cell. A real whole-row target would need a stretched link from one
cell (an `after:absolute after:inset-0` on a `relative` row), which fights the
"no control inside a linked row" rule as soon as a row holds a checkbox. Not built
until a screen needs it more than a trailing View button.

**8. Components deliberately NOT built**, so nobody adds them by reflex:

- **Server-side filtering for `combobox`.** It filters the list you pass it, in
  the browser. A searchable list too large to send needs a search callback, and
  a callback is a backend contract — the one thing nothing here has.
- **Upload transport for `file-upload`.** It is a field, not an uploader.
- **A date-and-time picker.** Two questions; a control that answers both does
  neither well.
- **Segmented control, rating, colour picker, rich text.** None have come up.

## The docs site (shipbytes.dev)

**https://shipbytes.dev/docs/design-system is generated from this repo**, by the site's
`scripts/sync-packages.mjs` at every site build. It clones **master** and reads:

| In this repo | On the site |
|---|---|
| `docs/getting-started.md` | `/docs/design-system` (the landing page) |
| `docs/README.md` | `/docs/design-system/components` **and the sidebar**: a component whose page is not in this table is missing from the navigation, and the site build warns |
| `docs/components/<slug>.md` | `/docs/design-system/components/<slug>` |
| `specs/README.md`, `specs/<slug>.md` | `/docs/design-system/specs`, `/specs/<slug>` |
| `docs/images/<slug>.png` | the screenshot on that component's page |
| git tags | `/docs/design-system/changelog` (there is no CHANGELOG.md here, so the GitHub release notes are the changelog people read: write them) |

Nothing on the site is written by the site. It converts these files, so the "seven
things" above are what the public documentation is made of, and a stale number here
(getting-started said "six" Alpine components for two releases while the code had ten)
is published as-is. **Counts and lists exist in four places:** README.md,
`docs/getting-started.md`, `docs/README.md` and the State section of this file. Adding a
component updates all four.

Rules the conversion imposes on the Markdown:

- Plain GFM. The first paragraph after the H1 becomes the page's meta description and
  social card text; H2s become sidebar sections and anchors. No raw HTML.
- Links resolve through the mapping above: `components/x.md`, `../getting-started.md#alpine`
  and `../../specs/x.md` work; anything else 404s on the site.
- Images as `![Alt](../images/<slug>.png)`, one light-and-dark image per component,
  from `npm run build:docs`.
- A callout `> **Needs Alpine.** See [getting started](../getting-started.md#alpine).`
  on every page of the ten Alpine components, and "— needs Alpine" in that
  component's row in `docs/README.md` ("— needs Alpine and the script" for the
  four that use the shared script, whose callout is the one above).

**Merging to master rebuilds the site automatically** (GitHub push webhook → the
rebuild Worker → the site's deploy workflow, ~2 minutes; branches and tags are
ignored). So do not merge a half-finished component to master: work on a branch until
the page, the table row and the screenshot exist. After merging, open
`https://shipbytes.dev/docs/design-system/components/<slug>/` and check the page, the
image and the sidebar entry.

The site repo is `shipbytes/shipbytes.dev` (local: `/var/www/shipbytes.dev`). The
converter lives there; if a Markdown construct renders wrongly on the site, the fix is
usually in `scripts/sync-packages.mjs`, not in rewriting the docs around it.

## Releasing

Tag `vX.Y.Z` and push tags — that is what `composer require ^1.0` resolves. A
consumer picks it up with `composer update shipbytes/blade-ui`.

```bash
npm test && npm run build
git tag -a v1.1.0 -m "…" && git push origin master --tags
```

**1.0.0 is the first tag of this history.** The repository was flattened to a
single commit before it, so there is nothing before v1.0.0 to compare against —
and the version is a real 1.x, not a 0.x: the component API is stable, and a
breaking change to a prop or a token name bumps the major.

**2.0.0 is the next release**, and it is assembled on `next-2.0`, one batch
branch and one PR at a time. Nothing on `next-2.0` is tagged or merged to master
until the owner says so; master stays on 1.x and keeps feeding the docs site
in the meantime.
