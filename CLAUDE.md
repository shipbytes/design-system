# Shipbytes Design System

A portable design system for new projects. Ships as two packages from one repo:

| Package | Registry | Who needs it |
|---|---|---|
| `shipbytes/blade-ui` | Composer | Laravel + Blade. Ships the compiled CSS, so no npm step. |
| `@shipbytes/design-tokens` | npm | Anything else — plain HTML, Svelte, a chart palette. |
| `@shipbytes/react` | npm (unpublished) | React. Lives at `packages/react/`, ported on demand — see Layout. |
| `@shipbytes/vue` | npm | Not built yet. See Known gaps. |

**The registries are separate front doors and each renders its own metadata.**
Packagist shows only the `description` field — no README — so that sentence is
the whole signpost there. npm renders README.md **from the package's own
directory**, and includes it automatically even when `files` does not list it:
the root README is what `@shipbytes/design-tokens` shows, which is why it opens
with a "which package do I need?" table rather than with Blade install steps.
`packages/react/` therefore carries its own README — the root one would never
reach its npm page.

Published at `github.com/shipbytes/design-system` and on Packagist as
`shipbytes/blade-ui`, so a consumer needs one `composer require` and no
repository block.

It was extracted from a production dashboard rather than designed in the
abstract. That is why the specs argue from measured usage ("zinc-500 was the
most-used class, 850 times") instead of taste. Those numbers are the evidence
for the rules and are worth preserving when editing.

## Layout

```
composer.json     shipbytes/blade-ui       ← both manifests live at the ROOT.
package.json      @shipbytes/design-tokens   Composer reads composer.json from
                                             the repo root and nowhere else.

src/              the service provider
config/           blade-ui.php — icon aliases, default icon size
resources/views/  the Blade components + the two pagination views
                  (everything here SHIPS to consumers — keep it lean)

tokens/           DTCG source. The only files edited by hand.
dist/             generated by `npm run build`. Never edit.
specs/            one markdown per component: anatomy, variants, states, a11y
docs/             CONSUMER docs: how to use each component, with screenshots
                  images/ is generated by `npm run build:docs` and committed
icons/            which Heroicons the system uses, and their v2 names
scripts/          build + test, and gallery.blade.php (dev-only, not shipped)
tests/            testbench render tests. Specimens.php IS the coverage.
phpunit.xml       dev-only; neither file ships to consumers

packages/react/   @shipbytes/react — its own package.json, tsconfig, vitest and
                  README, on branch `react`. Ported from specs/, never from the
                  Blade markup; src/index.ts is the live inventory of what
                  exists. Nothing here is shared with Blade but the tokens.
```

## Commands

```bash
npm run build        # tokens/ -> dist/   (run after ANY token change)
npm test             # tokens, then render, then behaviour
npm run test:tokens      # structure, WCAG contrast, theme collisions
npm run test:render      # renders every component through testbench
npm run test:behaviour   # drives every interactive one in a real browser
npm run build:gallery    # dist/gallery.html
npm run build:docs       # docs/images/ — re-run whenever a component's look changes
```

**None of these need a host application.** `scripts/render.php` boots Laravel
through testbench, so the gallery, the screenshots and the behaviour tests all
render through the same three lines and a clean clone needs nothing but
`composer install` and `npm install`.

`npm test` must pass before any commit. Three suites:

**Tokens** (`test-tokens.mjs`) — structure, WCAG contrast in both themes, theme
collisions. No Blade involved.

**Render** (`test-render.mjs`) — boots Laravel, renders every component in
`tests/Specimens.php`, and asserts every class it emits has a rule in CSS
compiled the way a *consumer* compiles it. Also enforces that every component
appears in the gallery, in the docs specimens, and has a documentation page.

**Behaviour** (`test-behaviour.mjs`) — drives every interactive component in a
real browser with real Alpine: focus traps, arrow keys, what the form actually
posts. **Skips with a warning when there is no Chromium** (`npx playwright
install chromium`), so a clean clone still goes green — read the warning.

## How to actually verify a change

```bash
npm run build:docs      # regenerates docs/images/ — light and dark, side by side
npm run build:gallery   # dist/gallery.html — every component on one page
```

**Look at the rendered output, in a browser, in both themes.** Every serious bug
in this repo's history was invisible in the source and obvious in a picture: the
panel inheriting the browser's default black at 1.4:1, the modal overflowing its
container, the dropdown detaching from its trigger in a flex row, the icon
rendering at the height of its panel.

`npm test` now covers a great deal of this — rendered classes, behaviour in a
real browser, and a contrast audit inside `build:docs` that fails the build on
anything under 3:1. What none of it can see is **a class that exists and is
wrong**. Both of these were green under `npm test` and obvious on screen:

- the modal's `max-h-[calc(100dvh-2rem)]` measured the viewport rather than the
  box it was centred in, so a long modal overflowed its container;
- the dropdown's root was `inline-block`, so in a flex toolbar it stretched to
  the row height and the menu opened from the floor of it.

So: still look at it.

## The consumer contract

```bash
composer require shipbytes/blade-ui
```

```css
@import 'tailwindcss';
@import '../../vendor/shipbytes/blade-ui/dist/tokens.css';
@import '../../vendor/shipbytes/blade-ui/dist/theme.css';
@source '../../vendor/shipbytes/blade-ui/resources/views';
```

Three lines, not four — `theme.css` brings its own `@custom-variant dark`. It
also carries `[x-cloak] { display: none !important }`, which Alpine expects every
project to write by hand: nine components mark their overlay root `x-cloak`, so
without it every dialog on the page renders open, backdrop and all, until Alpine
boots. That is our failure to ship, not the consumer's to remember.
No npm step: the composer package ships `dist/`.

Requires Tailwind v4. Dark mode is a `dark` class on `<html>`.

## Traps that have already bitten, in this repo

Each of these failed **silently**. None threw an error.

**Tailwind does not scan `vendor/`.** Without the consumer's `@source` line
every class the components emit is discarded as unused and everything renders
unstyled. "Unused" is not a failure, so nothing reports it. This is the single
most likely thing to go wrong in a new project.

**A class built at runtime is invisible to the scanner.** The icon component
composes `size-{$size}`; Tailwind reads source *text*, and `size="4.5"` is not
the string `size-4.5`. `theme.css` therefore carries an `@source inline(...)`
list, generated by `build-tokens.mjs` from the components plus a base range —
the base range exists so a *consumer* passing `size="7"` in their own view also
works. `npm test` fails if a component asks for a size the list misses. **Any
new component that builds a class from a prop needs the same treatment.**

**An `@theme` key overwrites Tailwind's, it does not add to it.** This is why
radius and shadow are named for the job (`control`/`panel`/`chip`,
`raised`/`float`/`overlay`) and not `sm`/`md`/`lg`. Reusing those keys would
resize every existing `rounded-lg` in the host app. `npm test` guards this with
a collision check whose only allowed entry is `--font-sans`.

**A `var()` inside a custom-property declaration resolves at the declaring
element.** `--color-x: var(--ds-x)` on `:root` bakes in the light value, and a
`.dark` ancestor cannot retroactively change it. `build-tokens.mjs` therefore
re-declares every themed mapping inside `.dark`. Remove that and dark mode dies
quietly for every semantic utility.

**Blade emits an uncompiled component tag as literal text** when the tag
contains a multi-line attribute-bag expression. Build the bag in `@php` and pass
it as `:attributes`. `build-gallery.mjs` fails the build if it sees `<x-ds::` in
rendered output, because that is the signature.

**Foreground tokens are `fg`/`fg-muted`, not `text-*`.** Tailwind's `text-*`
namespace serves both colour and font size, so `semantic.text-muted` would
generate the utility `text-text-muted`.

**`php artisan tinker --execute` rewrites the markup it prints.** PsySH's output
pipeline turns `...` into `..`, so every spread operator in a component lost a
dot on the way out. `build-gallery.mjs` rendered through tinker, so the modal's
focus trap and the dropdown's arrow-key handler both reached the gallery as
`[..$el.querySelectorAll(` — a syntax error, thrown at runtime, in a page that
looked perfect. Worse than a broken component: the gallery inventing a break
that does not exist in the shipped code. It now boots the framework directly and
carries a canary string through the render to prove nothing rewrote it.

**Blade's component-tag compiler is text-level, and does not know what a
comment is.** `<x-ds::tab-panel>` written inside a PHP doc comment in `@props`
was compiled into a real component invocation, in the middle of the props array,
and the file stopped making sense — the error was "Undefined variable $component"
pointing at a compiled file in storage, naming nothing. **Never write a component
tag in a comment.** Write `ds::tab-panel` without the angle brackets.

**A Blade DIRECTIVE inside a component tag's attribute is not compiled at the
call site.** `<x-ds::icon x-show="v === @js($option['value'])">` inside a
`@foreach` hands the directive to the CHILD as a literal string, where it is
evaluated in the child's scope and `$option` does not exist; `@unless` on a
component tag instead makes the tag parser give up and print the tag. `{{ }}`
echoes are fine there. Build the value in `@php` and echo it.

**An anonymous component turns only DECLARED props into variables.** Everything
else lands in `$attributes`. So `<x-ds::nav-item icon="home">` — where `icon` is a
SLOT — leaves `$icon` undefined, the `@isset` around it false, and the row renders
with no icon at all. The mirror case is just as quiet: a `<x-slot:head>` that no
component renders is simply dropped, which is how the table specimen, the docs
and the documentation screenshot were all wrong together. `npm test` now checks
both directions.

**A prop that resolves to classes in PHP cannot be driven from Alpine.** Every
`tone`, `variant`, `size` and `active` is a lookup of literal class strings, done
once at render time — which is the only reason Tailwind's scanner can see them.
So `::tone="item.tone"` binds an attribute nothing reads, and an `x-for` over a
toast list renders every toast neutral. Nothing errors. The repair has a second
trap inside it: Alpine's STRING form of `:class` only *adds* classes, so the
server-rendered `border-transparent` survives and the element carries both. Only
the OBJECT form removes a class the server put there. `specs/tabs.md` documented
the broken form for two releases; the working one is now a driven specimen in
`scripts/behaviour-specimens.blade.php` so it cannot drift back.

**`open` on modal, drawer and sheet is an lvalue, not an expression.** They
assign to it — `@click="{{ $open }} = false"` — so `open="mode === 'x'"` compiles
to `mode === 'x' = false`. The dialog OPENS, because reading is fine, and then
the ✕, the backdrop and Escape all do nothing, with a clean server log and one
console `SyntaxError`. `Support\OpenState` now refuses it at render time. The
check is deliberately shallow — comparison and logical operators only. It must
not grow into a JavaScript parser: a false positive here is worse than the bug,
because the bug at least renders.

**An anonymous component silently drops a slot it never renders.** `empty-state`
has no default slot — its body is `title`/`description` and the button goes in
`action` — so passing buttons the way every other component takes them rendered
nothing at all. It throws now. Same shape as the `<x-slot:head>` the table
ignored, and as `<x-ds::nav-item icon="home">` leaving `$icon` undefined.

**Tailwind v4 auto-detects sources on top of `@source`.** Compiling anywhere
inside the repo silently pulls in `scripts/gallery.blade.php`, `dist/gallery.html`
and the specs — all of which *mention* the classes the components emit. The
render test compiled against that passed while deliberately broken, because
something else in the repo happened to name the class. `@import "tailwindcss"
source(none)` plus one explicit `@source` is what makes the check mean anything.
A consumer's own import should auto-detect; ours must not.

## Conventions

- **Presentation only.** No Livewire, no Alpine, no state, no framework
  assumptions beyond Blade. Anything reactive is passed in by the host through
  attributes. This is what keeps the same markup usable from plain Blade, a
  Livewire component, or a Volt page.
- **A component is not done until SEVEN things exist.** In the same commit
  series, not as follow-up work:
  1. the component in `resources/views/components/`
  2. its **spec** in `specs/` — anatomy, variants, states, the a11y contract, and
     a "Do not" section. Sub-components (`table-cell`, `panel-row`) are covered
     by the parent's spec.
  3. a **specimen** in `tests/Specimens.php` — that list *is* the test coverage,
     so a variant missing from it is a variant nothing renders
  4. a **docs page** in `docs/components/` — usage, full prop table, examples
     against real Laravel, accessibility, and a "Don't" list
  5. a **specimen** in `scripts/docs-specimens.blade.php`, then
     `npm run build:docs` to generate its light/dark screenshot
  6. a **section in `scripts/gallery.blade.php`**, then `npm run build:gallery`.
     The gallery claims to render every component in both themes; six shipped
     without one and quietly made that false.
  7. for anything interactive, a **specimen and assertions** in
     `scripts/behaviour-specimens.blade.php` and `scripts/test-behaviour.mjs`

  `npm test` enforces 3, 4, 5 and 6. Nothing enforces 1, 2 and 7 but you.
  A component reported as done without its documentation page is unfinished.
- **Semantic props, not free-form styling.** `tone="danger"`, not
  `tile="bg-red-50"`. A prop that takes a class string is an escape hatch that
  becomes the norm — the sheet shipped with ten decorative hues that way.
- **Comments explain why, not what.** The reason a value is what it is, or the
  bug that made it necessary.
- **Never name the app this came from.** It is deliberately anonymous.

## State

**Built — 41 components**, plus `ds::pagination` and `ds::simple-pagination`:

accordion, accordion-item, alert, avatar, badge, bottom-nav, bottom-nav-item,
breadcrumb, breadcrumb-item, button, checkbox, combobox, date-picker, drawer,
dropdown, dropdown-item, empty-state, file-upload, icon, input, modal, nav-item,
panel, panel-row, radio, radio-group, select, sheet, sheet-item, skeleton,
stat-tile, switch, tab, tab-panel, table, table-cell, table-row, tabs, toast,
toast-region, tooltip.

**Every built component has a spec.**

Verified end to end: `composer require` from GitHub into a fresh Laravel app,
three lines of CSS, every component rendering styled in light and dark.

**Needs Alpine:** modal, drawer, sheet, dropdown, select, combobox, date-picker,
accordion, file-upload, tooltip — always. Plus
ONE optional prop each on checkbox (`indeterminate`), nav-item (`collapsedWhen`)
and toast (`dismiss`). Everything else is plain Blade and CSS, and nothing
anywhere needs Livewire.

The alert's dismiss used to be Alpine's `@click` and is now a plain `onclick`:
nothing else in that component needs JavaScript, and with `@click` the ✕
rendered, looked pressable, and did nothing at all in a host without Alpine.

Those six emit Alpine directives and own no state — the host declares it, the
component reads it. `dropdown` and `tooltip` scope their own, because their state
is local to one trigger and a kebab menu per table row would otherwise need a
wrapper `x-data` each. `select` is the one exception worth knowing: it scopes the
open flag AND a mirror of the chosen label, while the FORM value stays the host's
and posts through a hidden input exactly as a native `<select>` would.

Modal's and drawer's focus traps are written out longhand rather than using
`@alpinejs/focus`: **Alpine skips a directive it has no handler for**, so in a
host without the plugin `x-trap` is not an error, it is nothing at all — and
`aria-modal="true"` becomes a claim the DOM does not honour.

**Components render their state correctly before Alpine boots.** `select`
renders the selected option's tick and the trigger's colour from PHP, so there
is no flash of wrong state on first paint and the markup is right in anything
that never runs the JS. Bind for what moves; render what does not.

## Known gaps

Kept here so nobody has to rediscover them. Roughly in the order worth closing.

**1. No BLADE overlay knows where the viewport edge is.** `dropdown`, `select`,
`combobox`, `date-picker` and `tooltip` each take a placement and trust it.
`npm run test:behaviour` MEASURES the cost at the bottom of its run rather than
describing it — at the time of writing the date picker runs **32px below the
fold** when its trigger sits at the bottom of the window, while the dropdown and
the select still fit. A calendar is ~340px tall, so it is the one that bites.

There is a second half the measurement does not show: an absolutely positioned
overlay is also clipped by any ancestor with `overflow: hidden|auto`, so a
combobox in a scrolling modal body is cut off at the footer whatever the
viewport is doing.

**Closed in `@shipbytes/react`** (M4 batch), where the evidence justified the
trade: `src/lib/popover.tsx` is one hook and one portal — `strategy: 'fixed'`
plus `flip`/`shift`/`size` from `@floating-ui/react-dom`, rendered into
`document.body`. `combobox` and `date-picker` use it; `dropdown` already had the
same behaviour through Radix, which uses floating-ui itself. Both regression
tests assert the popover's parent is `document.body` while its trigger sits
inside an `overflow-y-auto` box.

**Still open for Blade**, which is what the number above is about: closing it
there means Alpine plus floating-ui as this package's first shipped JS
dependency, and no Blade consumer has asked yet.

**2. The npm package is unpublished.** `@shipbytes/design-tokens` does not exist
on the registry, so the `import { tokens } from '@shipbytes/design-tokens'` path
in the README does not work yet. Irrelevant to Blade consumers — the composer
package ships `dist/` — and only blocks a JS project.

**3. `fg-muted` and `danger` are under AA on the app's own ground.** 4.39:1 and
4.33:1 on `surface-sunken`, against the 4.5 they need; both are comfortable in
dark (7.56, 6.93). It matters for help text, a breadcrumb, or a form that sits on
the page rather than inside a panel.

Recorded as ADVISORY in `test-tokens.mjs` rather than fixed, because closing it
means moving `fg-muted` off zinc-500 — the most-used colour in the system. A
deliberate decision with a wide blast radius, not a quiet fix.

**4. The React port is partial, by design.** `packages/react/` (branch `react`)
exists and is built against the frozen specs — `@shipbytes/design-tokens` for
CSS, `cva` for the recipe layer, Radix for behaviour, `@heroicons/react` for
icons. No shared component code with Blade; only tokens, recipes and specs
travel.

Components are ported **on demand**, when a consumer needs one, rather than all
41 up front — so the gap is not "unstarted" but "not yet complete", and the list
of what exists is `packages/react/src/index.ts`, not this paragraph. A component
missing from that barrel has not been ported: reach for `specs/<name>.md` and
port it, never approximate it.

Two things the port does NOT inherit from Blade. Icons resolve from an injected
registry (`createIconRegistry` / `IconProvider`) instead of importing the
heroicons namespaces, because a `name` prop needs a runtime lookup and four
namespaces do not tree-shake — the package keeps only a small built-in floor for
icons its own components draw. And motion lives in `tokens/motion.json` as named
keyframes, because Radix unmounts on close and waits on `animationend`: a
utility-class transition never fires one and would never be seen.

**5. The gallery cannot show `sheet` or `bottom-nav`.** Both are `lg:hidden`, and
the gallery is a page a person opens on a desktop, so at that viewport they
render nothing. The gallery's sheet section is hand-drawn markup for this reason
and is the one place in it that is not the real component. The documentation
screenshots DO show them, because that script drives a 1000px viewport on
purpose. An `<iframe>` at phone width would fix it.

**6. The accordion cannot be found by find-in-page.** It is the ARIA disclosure
pattern, so a collapsed section is `visibility: hidden` and the browser's own
find will not reveal it. `<details>` would give that for free, and was the other
candidate — see specs/accordion.md.

**7. Components deliberately NOT built**, so nobody adds them by reflex:

- **Server-side filtering for `combobox`.** It filters the list you pass it, in
  the browser. A searchable list too large to send needs a search callback, and
  a callback is a backend contract — the one thing nothing here has.

  Still true of the Blade component. The React one carries the seam, because a
  React consumer already owns its own fetching and so the prop costs nothing:
  `filter={false}` turns the component's own filtering off and `onQueryChange`
  reports the typing. It still fetches nothing itself, and the default behaviour
  is the spec's.
- **Upload transport for `file-upload`.** It is a field, not an uploader.
- **A date-and-time picker.** Two questions; a control that answers both does
  neither well.
- **Segmented control, rating, colour picker, rich text.** None have come up.

## Releasing

Tag `vX.Y.Z` and push tags — that is what `composer require ^1.0` resolves. A
consumer picks it up with `composer update shipbytes/blade-ui`.

```bash
npm test && npm run build
git tag -a v1.1.0 -m "…" && git push origin master --tags
```

**1.0.0 is the first tag of this history.** The repository was flattened to a
single commit before it, so there is nothing before v1.0.0 to compare against —
and the version is a real 1.x, not a 0.x: the component API is stable, and a
breaking change to a prop or a token name bumps the major.
